## Shared picker producer

CLI and Desktop use the same app-server `model/list` contract, `ModelsManager` implementation, and model schema. They are separate consumers and may use separate app-server process instances.

- The CLI bootstraps a fixed in-memory catalog from `model/list` with hidden entries included.
- The CLI `/model` popup consumes that snapshot and selection emits model and reasoning-effort changes.
- The installed Desktop renderer also calls app-server `model/list`; its selection callback carries model and effort.
- The shared server path is `message_processor -> CatalogRequestProcessor::model_list -> ThreadManager::list_models -> ModelsManager`.

One bridge-generated complete catalog can therefore feed both unchanged picker implementations when both processes load the same Codex home and configuration. V1.1 acceptance must still exercise CLI and Desktop independently because sharing a producer does not make one consumer proof sufficient for the other.

## Catalog and route contract

The generated catalog is display and capability metadata, not provider-routing metadata:

- Native catalog rows and their unknown fields are copied byte-semantically into the generated catalog without adding `model_provider`.
- Admitted Grok rows are appended without `model_provider`.
- Every selectable row must have a non-empty, globally unique exact slug. Duplicate Native/Grok slugs fail catalog generation.
- The lifecycle publishes a separate private Native route-state file containing every exact Native slug and the captured Native upstream kind.
- The live Grok catalog remains the only Grok admission owner. A request routes to Grok only when its exact model equals a currently admitted Grok slug.
- A request routes to Native only when its exact model equals a slug in the published Native route state.
- Duplicate, unknown, partial, prefix, and suffix matches fail closed before either upstream is called.

The unchanged Codex consumer globally selects the bridge-owned `grok_codex_picker` custom provider for every row. That provider sends Responses traffic to the fixed loopback `/v1` base with a private fixed `x-grok-caller-capability` header, keeps `requires_openai_auth = true`, and advertises `supports_websockets = false`. The capability never appears in the provider URL. The bridge, not the picker schema or a Codex fork, owns the exact model dispatch boundary.

## Native and Grok transport separation

The exact Codex 0.148 source establishes two first-party Native Responses bases:

- ChatGPT-family authentication: `https://chatgpt.com/backend-api/codex`.
- OpenAI API-key authentication: `https://api.openai.com/v1`.

Phase J must capture the effective base before installing the loopback override and pass it explicitly to picker installation. Lifecycle admits only those exact first-party bases; the bridge does not inspect credentials or infer an origin. The captured origin and Native slugs are atomically published in `picker-native-route.json`.

For a Native request:

1. The bridge reads only a bounded decoded copy far enough to obtain `model`. Codex 0.148 zstd request compression is supported.
2. The original body bytes, including compressed bytes, are forwarded unchanged.
3. Incoming end-to-end headers, including Codex-owned OpenAI authorization and account metadata, are forwarded; hop-by-hop transport headers are regenerated.
4. The upstream status, end-to-end headers, and body/SSE bytes are streamed back without JSON, tool, event, or retry transformation.
5. The custom provider disables WebSockets in Codex configuration, so the official client selects its HTTP Responses path without attempting an upgrade.

For a Grok request:

1. Incoming OpenAI authorization is not copied into the Grok transport.
2. The existing `NormalizedResponsesRequest` projection, namespace restoration, xAI credential owner, origin-locked Grok client, and validated SSE reconstruction remain Grok-only.
3. `GROK_CODEX_BRIDGE_DISABLE=1` disables only Grok inference; an admitted Native route remains available.
4. Remote Grok compaction fails closed because no authoritative Grok compact contract has been established.

The Native transport module cannot access Grok credentials. The Grok transport receives no incoming request headers. This structural separation is the credential boundary.

## Lifecycle and activation boundary

Phase J owns one atomic publication unit:

- bridge-owned merged `picker-models.json`;
- bridge-owned private `picker-native-route.json`;
- marker-delimited root `model_provider = "grok_codex_picker"` and `model_catalog_json` plus `[model_providers.grok_codex_picker]` in Codex `config.toml`;
- provider settings `wire_api = "responses"`, `requires_openai_auth = true`, `supports_websockets = false`, `request_max_retries = 0`, `stream_max_retries = 0`, a fixed loopback `/v1` `base_url`, and private `http_headers.x-grok-caller-capability` caller authentication; the zero retry budget prevents one failed bridge request from multiplying inference attempts while this user-controlled provider is selected;
- versioned managed state with byte length and SHA-256 identities for every bridge-generated artifact and the managed config; the Native Codex catalog is an external read-only input, not a rollback artifact;
- an exact private sibling backup when `config.toml` pre-existed.

A pre-existing user-owned `model_provider`, `model_catalog_json`, `openai_base_url`, conflicting `grok_codex_picker` provider table, partial marker, unsafe file, or altered managed identity fails closed. When the managed config identity still matches, uninstall restores the exact prior config bytes and mode. When Codex Desktop has legitimately reserialized the TOML, uninstall and picker update instead parse the current file, require the two managed root keys and every picker provider field to match either the current header-auth block or the concrete pre-header capability-path V1.1 block, and remove only those managed keys/table plus any surviving markers. This preserves unrelated current Desktop or user values, tables, and mode; any changed managed value fails closed. The Native catalog path must remain a safe regular read-only input, but its refreshed bytes are neither compared, removed, nor restored. Generated catalog, Native route, state, and private backup identities remain exact managed artifacts. The isolated V1.0 `grok_bridge` profile remains a separate rollback-safe route; it is not used for V1.1 picker dispatch.

Activation requires the newly materialized bridge binary, explicit Phase J picker installation with the captured Native upstream, service restart, and a fresh CLI process or full Desktop/app-server restart. Root `model_provider`, `model_catalog_json`, the custom provider table, and route state are startup-owned. No live activation has occurred in this implementation session.

## Bounded codex-router lesson

The pinned reference demonstrates the transferable topology:

```text
native catalog + enabled external entries
    -> generated merged catalog
    -> root model_provider + model_catalog_json + custom provider table
    -> one local exact-model dispatcher
```

V1.1 transfers exact-slug classification, fixed-header loopback caller authentication, marker-delimited atomic configuration, original-path restoration, and generated-artifact rollback. It does not copy codex-router's hard-coded Native target, auth-file fallback, request reserialization, namespace transformation, LiteLLM or Chat conversion, hosted-tool injection, fixed provider registry, retry, failover, or unknown-model-to-Native fallback.
