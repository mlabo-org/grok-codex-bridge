- `ModelInfo`, `ModelPreset`, and app-server `Model` have no provider identity: [`openai_models.rs`](https://github.com/openai/codex/blob/711a5f8b3a6eb40134146ae9ec22fdcdda5e3170/codex-rs/protocol/src/openai_models.rs#L221-L268), [`model.rs`](https://github.com/openai/codex/blob/711a5f8b3a6eb40134146ae9ec22fdcdda5e3170/codex-rs/app-server-protocol/src/protocol/v2/model.rs#L89-L121).

## Phase I decision

Phase I transparent GPT passthrough is required for this independent bridge design.

With one merged catalog under the bridge provider, every selected model reaches the bridge. Current CLI and Desktop picker rows cannot switch a Grok row to the bridge and a GPT row to OpenAI. Avoiding passthrough would require upstream Codex/Desktop protocol and client changes that attach provider identity to model rows and selection. That alternative is outside this bridge's current product boundary.

The bridge must therefore dispatch strictly by admitted model identity:

- Grok models use the existing origin-locked xAI Responses path and never reach OpenAI inference.
- Native GPT models use a byte-preserving native upstream path and never receive xAI headers or Grok normalization.
- Native upstream URL, authentication, and request construction must be discovered from the current loaded Codex provider/auth contract; they must not be hard-coded from one auth mode.

## Reload and restart boundary

- Model and effort changes within the existing provider/catalog are live.
- A new thread reloads configuration, but an existing session's provider is stable.
- `model_catalog_json` and the static `ModelsManager` are startup-owned.
- CLI integration therefore requires a fresh CLI process.
- Desktop integration requires reconstruction of its Desktop-owned app-server; the safe guaranteed boundary is a full Desktop relaunch. Hot reload was not established and must not be claimed.

## Bounded codex-router lesson

The pinned reference demonstrates a feasible generated-catalog shape:

```text
native catalog + enabled external entries
    -> generated merged catalog
    -> root model_catalog_json
    -> ordinary Codex model/list picker producer
```

Its implementation globally redirects `openai_base_url` to its router and performs model-identity routing there. It therefore supports the Phase I conclusion but is not architecture authority. V1.1 may transfer only generated-catalog ownership, marker-delimited atomic config mutation, original-path restoration, and generated-artifact rollback lessons.

The following mechanisms are excluded: LiteLLM or Chat multi-hop routing, request or namespace conversion, hosted-tool injection, fixed provider/model registries, native-slug theft, automatic failover, and codex-router's router implementation.

## Bridge ownership for Phase H through Phase J

- `src/catalog.rs` remains the owner of admitted, refreshable Grok model IDs. The generated picker catalog consumes that set; it must not introduce a second fixed Grok registry.
- `src/lifecycle.rs` owns installed state, exact backups, manifest validation, doctor, and uninstall. Generated picker state and base-config mutation require explicit new manifest ownership and exact rollback records.
- The native catalog is never edited in place. V1.1 writes a bridge-owned generated copy.
- The current isolated V1.0 profile and `grok-codex` entry remain active safe-provider routes backed by the same service. They do not become a compatibility fork.
- `src/protocol.rs`, the Grok credential owner, and the xAI transport remain accepted V1.0 inputs. Only an observed Phase I protocol contradiction may return an affected boundary to those producers.
