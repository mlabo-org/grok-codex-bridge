## Catalog and provider contract

Accepted Codex commit `93655171c5` adds provider identity to the authoritative local catalog without changing the CLI or Desktop picker payload:

- A local `ModelInfo` row may carry an explicit `model_provider`. The selected model slug remains the picker handoff; core resolves provider identity from the exact local catalog row.
- Provider routing is admitted only for an exact slug match. Longest-prefix, namespaced-suffix, fallback metadata, and arbitrary unknown slugs do not inherit provider routing.
- Model slugs must be unique across the complete local catalog. Duplicate slugs and unknown provider IDs fail configuration loading.
- Once any row enables provider routing, every row must name a provider. A partial catalog fails configuration loading instead of falling back to the profile-wide provider.
- Provider metadata received from the OpenAI remote models endpoint or its cache is stripped. Only the locally configured static catalog is routing authority.
- Every selectable Native GPT row names `openai`; Codex uses the built-in OpenAI provider, resolves its managed authentication, and sends the request directly to its native upstream.
- Every selectable Grok row names `grok_bridge`; Codex uses the custom bridge provider. A custom provider with `requires_openai_auth = false` does not inherit the global OpenAI/ChatGPT `AuthManager`; explicit provider-owned auth mechanisms remain separate.

The existing app-server and picker schemas still need only model and reasoning effort from the consumer. CLI and Desktop already send the exact selected slug through the shared app-server/core path, so both unchanged consumers receive the provider decision server-side from the same complete catalog.

For an existing thread, a model settings update resolves the exact catalog row before committing settings and atomically rebinds the session provider for the next turn. A turn already in progress retains the provider with which it started; steering may update the persisted model/provider pair for the following turn without moving the active request. Provider-bound routing also applies to prewarm, compaction, review, retry notification state, and realtime setup.

## Phase I decision and activation boundary

The former Codex source-ownership blocker is resolved by accepted commit `93655171c5`. Provider selection now occurs in Codex before request authentication and transport construction:

1. Native GPT selection stays on built-in `openai`; Native credentials and traffic go directly from Codex to the native upstream and never traverse this bridge.
2. Grok selection uses `grok_bridge`; Grok normalization and upstream transport remain bridge-owned, and first-party OpenAI authentication is not inherited by that custom provider.

This repository must still not add a Native GPT reverse proxy, read OpenAI auth state, forward incoming OpenAI authorization, hard-code an OpenAI/ChatGPT upstream, redirect root `openai_base_url`, or activate a complete catalog under one global bridge provider.

Source acceptance is not runtime activation. Activation requires the exact combined Codex binary containing `b7d56464c2` and `93655171c5`, publication through the Phase J lifecycle owner, and a fresh CLI process or full Desktop/app-server restart. Until those conditions are met, the Phase H generated catalog remains a non-activated construction artifact because the installed runtime does not yet implement this contract.

## Reload and restart boundary

- In the accepted source, exact model selection can atomically update the effective provider for the next turn; an active turn remains bound to its starting provider.
- A new thread reloads configuration. Existing-thread model/settings updates use the already loaded authoritative catalog and do not hot-reload catalog bytes.
- `model_catalog_json` and the static `ModelsManager` are startup-owned.
- CLI integration therefore requires the exact combined binary and a fresh CLI process.
- Desktop integration requires the exact combined binary plus reconstruction of its Desktop-owned app-server; the safe guaranteed boundary is a full Desktop relaunch. Hot reload was not established and must not be claimed.

## Bounded codex-router lesson

The pinned reference demonstrates a feasible generated-catalog shape:

```text
native catalog + enabled external entries
    -> generated merged catalog
    -> root model_catalog_json
    -> ordinary Codex model/list picker producer
```

Its implementation globally redirects `openai_base_url` to its router, receives Codex's Native GPT authorization at the local router, and forwards that authorization to the native upstream after model-identity routing. It therefore demonstrates the exact credential-traversal design prohibited by the accepted V1.1 contract. It also parses and reserializes Native GPT request JSON, so it is not evidence for direct Native transport preservation. V1.1 may transfer only generated-catalog ownership, marker-delimited atomic config mutation, original-path restoration, and generated-artifact rollback lessons.

The following mechanisms are excluded: LiteLLM or Chat multi-hop routing, request or namespace conversion, hosted-tool injection, fixed provider/model registries, native-slug theft, automatic failover, and codex-router's router implementation.
