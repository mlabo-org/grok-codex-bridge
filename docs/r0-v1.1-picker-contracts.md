## Phase I decision and owner blocker

Phase I cannot be implemented inside this bridge while Native GPT authentication is forbidden from traversing the Grok bridge. The current Codex picker/provider contract exposes no third route between these two incompatible configurations:

1. Keeping the built-in OpenAI provider and redirecting root `openai_base_url` to the loopback service makes Codex resolve its current first-party authentication and attach it to the loopback request. Depending on the active auth mode, this can include a bearer credential, `ChatGPT-Account-ID`, caller-supplied managed headers, or request-scoped Agent Identity authorization. The bridge would necessarily receive Native GPT authentication before it could inspect the model and relay the request.
2. Selecting the existing `grok_bridge` custom provider keeps `requires_openai_auth = false`. Codex therefore supplies no first-party OpenAI authentication. The bridge cannot authenticate a Native GPT upstream without independently reading, copying, refreshing, or guessing credentials, all of which are outside its authority.

This is a source-ownership blocker, not a missing Rust transport implementation. Native request and SSE bytes could be relayed without Grok normalization only after a route had been selected, but the bridge cannot reach that point under the required authentication boundary.

The true owner is the current Codex picker/provider/session path. It must bind provider identity to a picker model or otherwise switch provider inside Codex before authentication is resolved:

- Native GPT selections must retain the built-in OpenAI provider so Codex resolves the native upstream and applies its managed authentication directly to that upstream.
- Grok selections must use the `grok_bridge` provider and its existing unauthenticated loopback caller handoff.
- CLI and Desktop selections must both carry the same provider decision, and an existing session must either support a verified provider transition or require a new provider-bound session.

Until that Codex-owned contract exists, this repository must not add a Native GPT reverse proxy, read OpenAI auth state, forward incoming OpenAI authorization, hard-code an OpenAI/ChatGPT upstream, or activate the merged catalog under one global bridge provider. The generated Phase H catalog remains a non-activated construction artifact.

## Reload and restart boundary

- Model and effort changes within the existing provider/catalog are live.
- A new thread reloads configuration, but an existing session's provider is stable.
- `model_catalog_json` and the static `ModelsManager` are startup-owned.
- CLI integration therefore requires a fresh CLI process.
- Desktop integration requires reconstruction of its Desktop-owned app-server; the safe guaranteed boundary is a full Desktop relaunch. Hot reload was not established and must not be claimed.

## Bounded codex-router lesson

The pinned reference demonstrates a feasible generated-catalog shape:

```text
native catalog + enabled external entries
    -> generated merged catalog
    -> root model_catalog_json
    -> ordinary Codex model/list picker producer
```

Its implementation globally redirects `openai_base_url` to its router, receives Codex's Native GPT authorization at the local router, and forwards that authorization to the native upstream after model-identity routing. It therefore demonstrates the exact credential-traversal design prohibited by the current Phase I requirement. It also parses and reserializes Native GPT request JSON, so it is not evidence for request-byte preservation. V1.1 may transfer only generated-catalog ownership, marker-delimited atomic config mutation, original-path restoration, and generated-artifact rollback lessons.

The following mechanisms are excluded: LiteLLM or Chat multi-hop routing, request or namespace conversion, hosted-tool injection, fixed provider/model registries, native-slug theft, automatic failover, and codex-router's router implementation.
